# Security and refactoring audit — 2026-09-06

The audit found exploitable access-boundary weaknesses and reliability risks in the original API. The changes below are implemented in the workspace, with regression tests. This is a source review and automated test assessment, not a penetration-test certification or a claim that the unfinished restaurant platform is ready for production.

| Finding in the original code | Mitigation |
| --- | --- |
| High: users/products CRUD exposed process-local records without authentication or ownership checks. Numeric IDs made records enumerable and mutable. | A guard returns 404 by default and in production. The example routes require both `NODE_ENV=development` and `ENABLE_DEMO_CRUD=true`. This contains the exposure; it does not invent a staff authorization model. |
| High: a known branch/idempotency key returned an order before checking its table session, request contents, or public-access expiry, including the concurrent-conflict recovery path. | Store a canonical SHA-256 request fingerprint and require matching session, fingerprint, and unexpired public access on both replay paths. Changed requests and historical unverifiable keys return 409 without the order capability. |
| High: database TLS explicitly disabled certificate verification; connection-string TLS options could also override application settings. | Verify certificates by default, support an explicit CA PEM, and reject URL TLS overrides. Explicit plaintext remains available for trusted local development. |
| High integrity risk: review-required payments could be overwritten by another transaction or a changed amount; identical mismatches emitted repeated events. Confirmed retries did not compare the amount. | Preserve recorded transaction ID and amount. Identical retries return the recorded state without writes; changed confirmations return 409. Non-pending records without confirmation data require reconciliation. |
| Medium: inventory requests had no line/quantity limits, monetary totals could overflow PostgreSQL integers, and case-varied UUIDs bypassed duplicate detection. | Bound orders to 100 products, 1,000 units per product, and 2,147,483,647 satang. Normalize UUID identity, validate header/string lengths, and reject null/blank optional size/spice fields. Preserve strict nested DTO validation and the existing 64 KiB HTTP body limit. |
| Medium: blank webhook configuration could authenticate a missing token; extensions did not enforce public-access expiry. | Fail closed on absent/blank webhook secrets, retain timing-safe comparisons, and require unexpired public access for extensions. |
| Medium dependency advisories: installed Fastify 5.11.3 and qs 6.15.3 appeared in npm's advisory report. | Pin patched Fastify 5.12.1 and qs 6.16.0 using overrides and regenerate the lockfile, keeping NestJS 11. Installation reported zero vulnerabilities. The advisory preconditions are not proof that every reported dependency issue was exploitable in these routes. |
| Reliability: rollback failures replaced the original error, broken clients returned to the pool, retries held connections during backoff, and idle pool errors lacked a handler. | Preserve the initiating error, discard failed-rollback clients, release before backoff, validate pool size/TLS flags, and handle idle client errors without logging connection secrets. |
| Performance: one locked menu query per product, caller-dependent inventory lock order, and no index beginning with `order_items.order_id`. | One parameterized batched menu query, database UUID lock order, Map-based association, and a unique `(order_id, product_id)` index. The index also enforces the inventory-update assumption of one product line per order. |
| Lifecycle: expiry batches could overlap, worker shutdown did not await active batches, and Redis shutdown could miss a pending connection. | Coalesce expiry work, drain active expiry/publication batches, and settle a pending Redis connection before closing. Reject new Redis operations during shutdown and invalid TTLs before connecting. |

Parameterized production SQL and explicit public order views were already present and are preserved. No concrete SQL-injection or HTML-rendering XSS path was found in the inspected API. The generic storage update also now ignores inherited and prototype-control properties; existing feature adapters already select allowed fields, so this is defense in depth rather than a demonstrated HTTP exploit.

The access-control and input-boundary changes follow [OWASP REST security guidance](https://cheatsheetseries.owasp.org/cheatsheets/REST_Security_Cheat_Sheet.html) and [NestJS validation guidance](https://docs.nestjs.com/techniques/validation). Dependency fixes address the published [Fastify validation advisory](https://github.com/advisories/GHSA-w2qp-rph6-63g4), [Fastify proxy advisory](https://github.com/advisories/GHSA-3m5p-2c4r-xxw2), and [qs denial-of-service advisory](https://github.com/advisories/GHSA-4mjr-xmp4-gh2g).

## Refactored code and architecture

- [Order policies](src/orders/order-policy.ts) isolate canonical request identity, bounded order validation, and exact integer-money arithmetic for direct testing.
- [Orders service](src/orders/orders.service.ts) retains transactional orchestration, uses a separate table-session row type, and centralizes replay authorization. Input objects are not reordered or mutated.
- [Payments service](src/payments/payments.service.ts) reads confirmation evidence with the locked payment, avoiding an extra duplicate lookup. A materialized locking CTE ensures reservation eligibility is evaluated against the database clock after acquiring locks, avoiding application-clock skew and pre-lock expiry decisions.
- [Database service](src/database/database.service.ts) owns connection security and transaction failure/retry policy.
- [Demo guard](src/common/demo-only.guard.ts) makes the boundary around unauthenticated examples explicit and independently testable.
- TypeScript `strict` mode is enabled. DTO/entity definite-assignment assertions describe framework-populated fields; optional fields retain explicit types and runtime validation.

Menu reads fall from N SQL round trips to one. Total successful creation queries fall from `3N + 7` to `2N + 8`; per-item writes remain. In-memory lookup/association is O(N), while canonical hashing and database lock sorting require sorting. No throughput or latency improvement was measured against a live database. The branch daily-counter row remains a serialization point and must be measured under representative load.

## Tests and verification

The baseline had 170 passing unit/isolated HTTP tests. The expanded suite has 256 passing tests across 17 suites. Coverage is 99.18% statements, 87.22% branches, 97.56% functions, and 99.62% lines; production bootstrap is excluded by the existing coverage configuration. Coverage includes framework decorator branches and is not evidence of database concurrency correctness.

`npm run check` passed lint, strict typechecking, the coverage gate, and the production build. After the final small SQL change, typechecking/build and the affected payment tests were rerun. The npm installation audit reported zero vulnerabilities after dependency updates. `git diff --check` found no whitespace errors.

Added coverage includes happy paths, changed and cross-session idempotency retries on both lookup paths, expired capabilities, rejected production CRUD, blank secrets, null/blank optional input, oversized orders, invalid quantities, integer overflow, preserved payment evidence, retry exhaustion, rollback failure, pool release before backoff, concurrent worker calls, shutdown races, invalid Redis TTLs, and inherited/prototype-control fields.

[PostgreSQL integration tests](test/database.integration-spec.ts) now apply both migrations and cover replay ownership, immutable payment evidence, expiry enforcement, and opposite-order multi-product contention, alongside the existing rollback/oversell/payment-race tests. These tests were **not executed locally**: `TEST_DATABASE_URL` is unset and the Docker daemon is unavailable. The existing CI workflow provides PostgreSQL and runs this suite. No live Kafka, Redis, TLS handshake, or load test was performed.

## Rollout and remaining release requirements

1. Apply [migration 002](database/migrations/002_order_request_fingerprint.sql) once before deploying the new application. Existing duplicate order/product rows will cause index creation to fail; inspect and reconcile them rather than deleting financial data automatically. Index creation on a large table needs a planned migration window. Drain old writers to prevent new orders without fingerprints during rollout.
2. Historical null-fingerprint orders retain their public-link behavior, but their idempotency replays fail closed with 409. Configure verified TLS, remove URL TLS flags, and explicitly opt in to local demo routes only when needed. [README](README.md) describes the changed contracts.
3. Before public production exposure, implement the documented official KBank signature/payload adapter and reconciliation workflow. The interim shared token is not equivalent to bank signature verification. Staff endpoints still require real authentication, tenant authorization, and durable persistence before they can replace the disabled examples.
4. Public session/order routes need deployment-level rate limits and brute-force protection. Request bounds do not limit request frequency. Public order UUIDs remain bearer capabilities; prevent their leakage through logs, referrers, or caches. Configure HTTPS and suitable response/cache policies at ingress.
5. Validate database roles and tenant isolation. Merely enabling RLS without policies does not establish backend isolation; owners and BYPASSRLS roles can bypass it. Verify every exposed table/role before permitting direct database access.
6. Outbox delivery remains at least once: a broker acknowledgement followed by a failed database commit can publish the same event again. Consumers must deduplicate stable event IDs; cross-replica publication order is not guaranteed by `SKIP LOCKED`. Broker I/O still holds a transaction, so test pool pressure and shutdown timeouts under outage conditions. Redis retry/queue limits and retention of sessions, orders, and outbox data also need deployment capacity planning.

The full changelog is in [REFACTORING_CHANGELOG.md](REFACTORING_CHANGELOG.md). Production readiness remains contingent on these integration checks and existing unfinished platform capabilities.
